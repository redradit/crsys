An honest premise

This has not been independently audited.

It is a solo project. It was written carefully, it reimplements no cryptographic primitive — everything comes from pyca/cryptography, backed by OpenSSL — and it has a test suite that deliberately attacks it. That is not the same thing as review by people whose job is breaking things.

For data whose compromise would have serious consequences, use age or GnuPG. Their value is not the algorithm; it is the number of competent people who have tried to break them and failed.

What CRSYS offers instead is a small, readable protocol, a normative specification anyone can implement against, and a public record of every defect found so far — including the serious ones. Most projects hide that list. Here it is the point.

Quickstart

Three commands, or three lines.

A keypair, a sealed file, and the check that actually matters on the way back out. Real commands, real output — nothing here is mocked up.

bash
# make an identity — prints the fingerprint you verify out of band
$ python -m crsys keygen -o alice -c "Alice <alice@example.com>"
Fingerprint : da60-ed69-9846-a0e6

# encrypt for bob, signed by alice, in one pass
$ python -m crsys encrypt -r bob.pub -s alice.key -i contract.pdf -o contract.crsys
Encrypted 48213 bytes -> 48431 bytes  [chacha20poly1305]

# decrypt — and REFUSE it unless alice really signed it
$ python -m crsys decrypt -k bob.key -i contract.crsys -o out.pdf --require-signer alice.pub
Decrypted 48213 bytes  ·  signed by da60-ed69-9846-a0e6 ✓
# the same round trip, from Python
from crsys import KeyPair, encrypt_bytes, decrypt_bytes

alice = KeyPair.generate()
bob   = KeyPair.generate()

sealed = encrypt_bytes(b"the note", [bob.public_key], signer=alice)
result = decrypt_bytes(sealed, bob, expected_signer=alice.public_key)

# result.plaintext == b"the note", and the signature is checked

--require-signer is the important part: without it, an unsigned message is accepted silently. With it, decryption fails when the signature is missing or belongs to somebody else.

What it does

Three jobs, done plainly.

Encrypt to anyone

A fresh ephemeral key per recipient per message. Two encryptions of the same file are uncorrelated. One message, many recipients, each with their own sealed envelope.

ChaCha20-Poly1305 · AES-256-GCM

Sign, or don't

An Ed25519 signature binds the sender's whole identity, the header, and the plaintext to the message — so a recipient cannot re-address or re-attribute it. Optional, because a signature is non-repudiable and that is not always what you want.

Ed25519 · covers header + recipients

Protect keys at rest

Private keys are held under a memory-hard KDF, with the cost parameters authenticated so they cannot be downgraded. On Windows the key file's ACL is tightened and verified, not just flagged read-only.

Argon2id · scrypt fallback

How it works

One pass, five moves.

No primitive is invented here. The design is in how standard ones are composed — and the whole of it fits in one line of data flow.

01

Ephemeral key

A throwaway X25519 keypair, generated fresh for this recipient, this message.

02

Agree

ECDH against the recipient's public key yields a shared secret only they can recompute.

03

Derive

HKDF-SHA256 turns it into a key, binding both public keys so no third party can be substituted.

04

Seal

The payload is sealed in AEAD chunks — the header is authenticated with every one.

05

Sign

Optionally, Ed25519 over the header, the recipients and the plaintext hash. Then it's a container.

The record

12

defects found, and fixed.

Eight came from the fuzzer. Three came from reading the code against RFC 9180 and the EdDSA literature. One came from a stranger on Stack Exchange. The worst survived every test and every fuzzing campaign — it was caught only by comparing the construction against published analysis of Ed25519. The list is public because a project that hides its bug history is asking you to trust it blind.

  • #9A universal signature forgery. With the Ed25519 identity point as the signer's key, one fixed signature verified every message — a valid signature from no private key at all.shipped in 0.1.0 · fixed in 0.2.0 · 0.1.0 withdrawn
  • #1The signature did not cover the X25519 half of the sender's identity, so a valid signature could be re-attributed to a different fingerprint. — code review
  • #7KDF cost parameters were bounded individually but not by resulting memory: a hostile key file could ask for ~17 TB and turn opening it into a denial of service. — fuzzer
  • #11The X25519 shared secret was never checked for the all-zero value that RFC 9180 makes a MUST — safe here only by OpenSSL's grace, and the spec documented the wrong safeguard. — RFC review
  • #12The documentation itself overclaimed: it presented key validation as key commitment. Two different properties; only one was present. — outside reviewer

The full list, with how each was caught, is in the README and SECURITY.md.

Threat model

What it does, and does not, protect.

The second column is the one that gets systems broken, so it is not buried. Read it before trusting anything to the first.

Protects against

  • Reading the content without the right private key — it would take breaking X25519 or ChaCha20-Poly1305.
  • Any modification. The suite flips every bit and truncates at every offset; every case is rejected.
  • Truncation and reordering — the chunk counter and a final-chunk flag live in the nonce.
  • Re-addressing a signed message — the signature covers the recipient list.
  • Identity substitution — a signature is attributed by all 64 bytes of the key, never a short fingerprint.
  • KDF downgrade — the cost parameters are authenticated.

Does not protect against

  • Trusting the wrong key. There is no PKI. Verify fingerprints over a separate channel — the one link software cannot close for you.
  • A signature from an unknown key. It proves someone signed, not who. Pin the expected signer.
  • A compromised endpoint. Keyloggers and malware beat any encryption.
  • Later decryption. No forward secrecy: a stolen long-term key opens past messages.
  • Quantum computers. X25519 and Ed25519 are not post-quantum.
  • Metadata. File size, timing and recipient count stay visible.

Wanted: a second implementation

Break the spec, not the code.

The largest gap in this project is that no independent implementation exists, so no ambiguity in the specification has ever been shaken out by anything but the code reading its own mind. That is not a gap the author can close.

  1. Write a decrypter from SPEC.md alone — without reading the Python.
  2. Check it against the nine frozen vectors (private keys included, published on purpose).
  3. If it disagrees with a vector, or you had to open the source, the specification is what failed — and that is the finding worth having.

Two version numbers, meaning different things

The format almost never moves.

A file you encrypt should still open years from now. So the container format has its own version — currently 1, and it has never changed — separate from the software's. A new release fixes bugs; it does not strand your files.

Software
0.2.1

Moves with every fix and feature. Pre-1.0, and honest about it: interfaces and internals can still change.

Container format
1

Frozen. Pinned by conformance vectors the test suite checks on every run. A change to the bytes is a new format version, never a quiet patch.
